# Codebase X-Ray

**An engineering-health report for any public GitHub repository.**

Codebase X-Ray reads a bounded, explicitly-disclosed sample of a repository's own files — manifests, source modules, tests and docs — and returns a structured report: statistics, language mix, a module graph, six sector scores, evidence-backed findings and an optional explanation layer.

Every number is either measured from content that was actually fetched or labelled as an estimate. Nothing is generated by a model. The product has two deliberately separate layers:

| Layer | What it does | Depends on credentials? |
|---|---|---|
| **X-Ray engine** | inspects, measures, detects, scores | **No client credentials** — production needs a server-side GitHub token and shared quota store |
| **AI assistant** | explains and prioritises what the engine found | Yes, optional (`AI_API_KEY`) |

Built for developers evaluating an unfamiliar codebase, maintainers preparing a project for contributors, and reviewers who want a fast, honest read on structure, testing, security hygiene and documentation.

> **Scope.** This is a heuristic analyzer, not a security audit, a CVE scanner or a full static-analysis platform. It inspects a bounded sample of large repositories and states the coverage on every report.

---

## Features

- **Live analysis** of any public GitHub repository — server-side; repository code is never executed.
- **Offline demo** of a fictional repository, labelled `DEMO DATA`, so the UI works with no network and no quota.
- **Language-aware parsing** — TypeScript/JavaScript through the TypeScript compiler API (real syntax tree), Python through an indentation parser, other languages through a generic import scanner. Each parser declares whether it is AST-backed.
- **Adaptive inspection budgets** — 48 / 72 / 96 / 128 files by repository size, with byte, concurrency and deadline caps that are hard limits, never silent truncation.
- **Measured coverage** — inspected vs eligible files and bytes, parsed files, parse failures, unresolved imports, and whether GitHub truncated the tree.
- **Architecture graph** — workspace packages, top-level modules, a root module for root-level entry files, and imports resolved through relative paths, `tsconfig`/`jsconfig` aliases and workspace package names. Unresolvable internal imports are counted, never hidden.
- **Measured code quality** — function spans, parameter counts, cyclomatic-complexity proxies, class sizes and normalised duplicate blocks — all with file/line references.
- **Security signals** — known credential formats (values redacted before they leave the scanner), committed env files, key-like filenames, plus risk patterns (eval, shell interpolation, raw HTML sinks, SQL interpolation, disabled TLS verification, weak hashes, permissive CORS, unverified JWT reads) each with a verification step.
- **Six sector scores** with confidence labels, uniform small-repository damping, and a versioned methodology.
- **Evidence model** — every finding carries category, confidence, detection method, limitation and file references.
- **Honest degradation** — sampling, truncation, budget exhaustion and mid-scan rate limits become `PARTIAL ANALYSIS` with quantified coverage.
- **Optional AI assistant** — explains findings and architecture from the analysis object only; never invents measurements. Renders a disabled state when unconfigured.

## Architecture

```
Browser (React 19 client components)
  • URL form uses the same parser as the API
  • Demo mode: local fixture, no network
  • Live mode: POST /api/analyze, results appear when the server answers
                    │
                    ▼
POST /api/analyze  (Node runtime, force-dynamic, maxDuration 60)
  origin check → 4 KiB body cap → parseRepoUrl (non-demo)
  → production config gate → shared per-client/global quota
  → demo branch / scan lock → hourly budget → HttpGitHubClient → runAnalysis()
                    │
                    ▼
Analysis pipeline (pure, deterministic, network-agnostic)
  1 repo metadata → 1 recursive tree → adaptive N blobs
  prune (ignored/binary/oversized) → prioritize → bounded fetch
  → parsers (TS AST / Python / generic) → extractors
  → quality metrics → security rules → architecture profile
  → graph resolution → detectors → sector scoring → insights
                    │
                    ▼
RepoAnalysis JSON → /00 manifest · /02 score · /03 structure · /04 graph
                  · /05 issues · /06 insights · /07 status
                  · /08 coverage & limitations · /09 assistant
```

The engine never imports the HTTP client: `runAnalysis(client, …)` accepts anything implementing `GitHubClient`, which is why the whole pipeline is testable against fixtures without spending quota.

### Parser capability

| Parser | Languages | Method | Accuracy |
|---|---|---|---|
| `typescript` | `.ts .tsx .mts .cts .js .jsx .mjs .cjs` | TypeScript compiler API (`ts.createSourceFile`) | AST — imports, exports, function spans, params, complexity, classes |
| `python` | `.py` | Indentation-based structural parse | Structural only — not an AST |
| `generic` | Go, Rust, Java, C#, Ruby, PHP, C/C++, Swift, … | Import-line scanning | Imports + TODOs only; no function metrics |

Adding a language means adding one module implementing `LanguageParser` and registering it — nothing downstream changes.

### Quota implications

A live scan costs metadata + tree + up to the adaptive blob budget (48–128 files), plus bounded retries. The unauthenticated GitHub limit is **60 requests/hour per source IP**, so a token is effectively mandatory for a public deployment.

Production uses a **shared atomic quota store** (Upstash/Vercel KV) with per-client and global counters. Counters are checked and incremented in one operation; rejected requests do not consume capacity. Admission control estimates the scan's GitHub request cost and refuses before tree/blob retrieval when the remaining quota and safety reserve cannot cover it. A separate hourly scan budget and a 25-request safety reserve bound burst spending. These are conservative estimates, not a GitHub reservation guarantee.

## How live analysis works

1. **Validate** — parsed server-side; `github.com/owner/repo`, `owner/repo`, `.git` suffixes and `/tree/...` links are all accepted.
2. **Tree** — recursive tree request. GitHub caps it at 100,000 entries; truncation marks the scan partial.
3. **Prune** — ignored directories, binary extensions and files over 256 KiB are excluded and counted.
4. **Prioritize** — root README → manifests → workspace manifests → entry points/config → source → tests/fixtures → docs → other → vendored/minified.
5. **Budget** — an adaptive tier decides how many files may be read (48/72/96/128) within byte, concurrency and deadline limits.
6. **Parse** — each fetched source file goes through the best available parser; failures are counted, not hidden.
7. **Analyze** — extractors, quality metrics, security rules, architecture inference and graph resolution run over parsed structure plus tree metadata.
8. **Report** — findings carry category, confidence, method, limitation and file references. Secret values never leave the scanner.

### Coverage disclosure

Every report states: inspected vs eligible files/bytes, parsed files, parse failures, unresolved imports, tree truncation, and the budget that was applied. When coverage is below 100%, the report is marked `PARTIAL` and the UI shows a banner. A partial scan is never presented as complete.

## Scoring methodology

Six sectors — code quality, security, testing, architecture, documentation, maintainability — each 0–100, combined by documented weights.

- **Versioned.** `analysis.scoringVersion` identifies the methodology. Scores are only comparable within one version.
- **Damped uniformly.** Small repositories (few files/LOC) are pulled toward the neutral 50 in *all six* sectors, because low evidence should not read as excellence.
- **Confidence-labelled.** Each sector reports `verified`, `high`, `heuristic` or `incomplete`.
- **No fabricated precision.** Testing scores use the test/source *file ratio*; no coverage percentage is inferred. Documentation scores measure existence and size, not prose quality.
- **Neutral, not positive, when empty.** A sector with no evidence returns 50 with an explicit explanation.

Weights and thresholds live in `src/lib/analysis/scoring/weights.ts`.

## Evidence model

Every finding includes:

```
id · category · title · severity · confidence · detectionMethod
file · line · detail · evidence[] · limitation · recommendation
```

- `verified` — exact measurement of fetched content (e.g. line count, committed file).
- `high` — deterministic detection over content/metadata (e.g. credential pattern, AST span).
- `heuristic` — structural inference (e.g. architecture pattern, duplicate similarity).
- `incomplete` — insufficient evidence; no claim is made.

## AI assistant (optional)

`POST /api/ai` explains the analysis. It cannot scan, measure or modify anything.

- **Grounded.** The provider receives a compact projection of the analysis (counts, scores, findings, cited paths) — never repository file contents, never tokens.
- **Validated.** Responses must be strict JSON; citations referencing paths or finding IDs that are not in the analysis are **dropped**, and the count of dropped citations is shown to the user.
- **Fail-closed.** Missing credentials → `503 AI_UNAVAILABLE` and a disabled panel. Provider errors → explicit failure, no invented fallback answer.
- **Modes.** Beginner / developer / engineering are presentation levels over the same evidence.
- **Prompt-injection aware.** Repository-derived text is passed as data with an explicit instruction not to follow instructions found inside it.
- **Bound to a real scan.** `/api/analyze` issues a short-lived HMAC token over the exact analysis payload; `/api/ai` rejects modified payloads and payloads presented under a different scan. This is an expiring integrity binding, not a single-use nonce: the same token can be replayed for the same payload until it expires. Production requires `AI_ANALYSIS_SECRET`.
- **Cost-bounded.** Per-client burst quota, global daily request ceiling, 900 output tokens and a provider timeout. Hosted Vercel AI is disabled unless `AI_PUBLIC_ENABLED=1`.

## Limitations (explicit)

- Large repositories are sampled; the sample is prioritised but not statistically representative.
- LOC and language shares are exact only for fetched files; the rest are estimated from tree byte sizes.
- Dependencies are read from root manifests only; workspace aggregation and transitive graphs are not built.
- Python parsing is structural, not AST-based; other languages get imports and TODOs only.
- Duplicate detection compares normalised 6-line blocks — a similarity signal, not semantic equivalence.
- No code execution, no test execution, no coverage ingestion, no CVE database.
- Architecture patterns are inferred from structure and carry an explicit confidence label.
- Quota identity is IP-header based; it is a coarse anonymous bucket, not authentication. The global budget is the backstop.
- No persistence, history, sharing, export or accounts yet.

## Deployment

The app needs a Node runtime (not Edge) because the analysis route uses `Buffer` and the TypeScript compiler API. Set `GITHUB_TOKEN` (fine-grained, public read-only), `UPSTASH_REDIS_REST_URL`/`_TOKEN`, and `AI_PUBLIC_ENABLED=1` plus `AI_ANALYSIS_SECRET` only if AI is intentionally enabled. On hosted Vercel, the opt-in applies to both production and preview URLs, so preview deployments do not silently become AI spending surfaces.

## Testing

```bash
npm test          # unit + integration, fixtures only
npm run typecheck
npm run lint
```

The suite covers URL parsing, the full pipeline against a fake GitHub client, pruning/prioritisation, dependency extraction, security redaction, scoring, parser behaviour, graph resolution, quality metrics, AI response validation, API validation, controlled partial results for failed/malformed blobs, and component states (zero findings, coverage disclosure, AI disabled/available).

Playwright covers the landing form, demo report, AI-disabled state, cancellation, upstream errors, responsive widths, keyboard reachability and axe scans of the landing page and full demo report. It is not a screen-reader audit.

`npm run benchmark` runs the real pipeline over labelled fixtures with known expected findings and reports precision/recall/F1, critical-path selection recall and parser-depth assertions. It is a conformance guard, not a claim of accuracy on arbitrary repositories.
