# Codebase X-Ray

**An engineering-health report for any public GitHub repository.**

Codebase X-Ray reads a bounded sample of a repository's own files — manifests, source modules, tests and docs — and returns a structured report: repository statistics, language mix, a module graph, six sector scores, evidence-backed issues and prioritised insights. Every number is derived from GitHub's tree/blob API or labelled as an estimate; nothing is generated by a model.

Built for developers evaluating an unfamiliar codebase, maintainers preparing a project for contributors, and reviewers who want a fast, honest read on structure, testing, security hygiene and documentation.

> **Scope:** this is a heuristic analyzer, not a security audit or a full static-analysis engine. It inspects a bounded sample of large repositories and says so in the report.

---

## Features

- **Live analysis** of any public GitHub repository (server-side, no repository code is ever executed).
- **Offline demo mode** with a fictional repository, so the UI works without network or quota.
- **Repository structure** — file tree, exact/estimated LOC split, language distribution, dependency count.
- **Architecture graph** — workspace packages found from `package.json` / `pnpm-workspace.yaml` / `lerna.json`, external dependencies, and import edges resolved from fetched source.
- **Six sector scores** (code quality, security, testing, architecture, documentation, maintainability) with the signals behind each one.
- **Evidence-backed issues** — committed env files, high-confidence credential patterns (values redacted), oversized modules, missing license/README, deep nesting, god directories, missing CI, unpinned dependencies.
- **Honest degradation** — truncation, sampling, budget and rate-limit conditions become visible warnings and a `PARTIAL ANALYSIS` banner instead of a silent "complete".
- **DEMO vs LIVE labelling** on every result panel.

```
│  • URL form validation, demo mode (no network)                       │
└───────────────────────────┬──────────────────────────────────────────┘

│ Next.js Route Handler — Node runtime                                 │

│  → parseRepoUrl → demo? → runAnalysis()                              │
└───────────────────────────┬──────────────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Analysis pipeline (pure, deterministic, network-agnostic)            │
│                                                                      │
│  GitHubClient (server-only)                                          │
│    1 repo metadata → 1 recursive tree → ≤24 blobs                    │
│                            │                                         │
│  tree-utils: prune ignored/binary/oversized → prioritize manifests,  │
│              source, tests, docs (vendored content last)             │
│                            ▼                                         │
│  extractors: stats · dependencies · testing · docs · security ·      │
│              architecture                                            │
│                            ▼                                         │
│  graph builder (workspace globs + import resolution)                 │
│  issue detectors (evidence only) · sector scoring · insights         │
└───────────────────────────┬──────────────────────────────────────────┘
                            ▼
        RepoAnalysis JSON → /00 manifest, /02 score, /03 structure,
        /04 graph, /05 issues, /06 insights, /07 system status
```

The engine never imports the HTTP client: `runAnalysis(client, …)` accepts any object implementing the `GitHubClient` interface, which is what makes the whole pipeline testable with fixtures.

## Environment variables

| Variable | Required | Scope | Purpose |
|---|---|---|---|
| `GITHUB_TOKEN` | No | **Server only** | Raises GitHub REST quota from 60 to 5,000 requests/hour. Never prefix with `NEXT_PUBLIC_`. |

The app runs without any environment variables. See [.env.example](.env.example).

**Quota implications.** A live scan costs about **26 requests** (1 repository, 1 recursive tree, up to 24 blobs). The unauthenticated limit is **60 requests/hour per source IP**, shared by everyone behind that IP; a single scan therefore consumes ~43% of it. A token is strongly recommended for any public deployment. When quota is exhausted the API returns `429` with the reset time, and the UI shows the real error rather than retrying in a loop.

## How live analysis works

1. **Validate** — the URL is parsed server-side; only `github.com/<owner>/<repo>` (or `owner/repo`) is accepted.
2. **Tree** — `GET /repos/:owner/:repo/git/trees/:branch?recursive=1`. GitHub caps this response at 100,000 entries; a truncated tree degrades the scan to partial.
3. **Prune** — ignored directories (`node_modules`, `dist`, `.next`, `vendor`, …), binary extensions and files over 256 KiB are excluded and counted in a warning.
4. **Prioritize** — remaining blobs are ordered: root README → root/workspace manifests → package manifests → entry points/config → source → tests/fixtures → docs → other → vendored/generated/minified content. Category caps stop a monorepo from filling the budget with one file type.
5. **Fetch** — at most **24 files**, 256 KiB each, 3 MiB total, 6 concurrent, with an 8 s per-request timeout and a 25 s pipeline deadline.
6. **Analyze** — extractors and detectors run over the fetched text plus tree metadata. Secret values are never stored or returned — only pattern name, file and line.
7. **Report** — scores, issues, graph and warnings are serialized as one typed `RepoAnalysis` object.

### Demo mode

The bundled fictional repository (`nebula-labs/orbit-forge`, or any request with `demo: true`) returns a deep clone of a static fixture. No network request is made, no quota is spent, and every panel is labelled **DEMO DATA**. It is also the fallback for reviewers who do not want to configure a token.

## Scoring methodology

Overall score = weighted mean of six sector scores (each 0–100):

| Sector | Weight | Main signals |
|---|---|---|
| Code quality | 20% | Oversized-module ratio, largest-file LOC share, TODO/FIXME density, nesting depth |
| Security | 20% | Committed `.env` files, high-confidence credential patterns, secret-like filenames; bonuses for `SECURITY.md`, lockfile, `.env.example` |
| Testing | 15% | Test-to-source file ratio (full marks at 0.5), detected framework, test config |
| Architecture | 15% | `src`/workspace layout, oversized-module pressure, deep paths, god directories |
| Documentation | 15% | README size, CONTRIBUTING, license, `docs/`, API schemas, `.env.example`, `SECURITY.md`, markdown volume |
| Maintainability | 15% | Direct dependency load vs a ceiling of 40, CI workflows, LOC concentration, lockfile, version pinning |

Details and every constant live in [`src/lib/analysis/scoring/weights.ts`](src/lib/analysis/scoring/weights.ts).

Two deliberate dampers prevent misleading certainty:

- **Small-repository damping** pulls sector scores toward the neutral 50 when evidence is thin (< 10 source files or < 1,000 LOC).
- **Sample disclosure** — when fewer files were inspected than the tree contains, partial warnings are shown and the score panel states the sample size explicitly.

These scores are heuristics. They are useful for spotting patterns, not for compliance sign-off.

## File sampling and performance limits

All budgets live in [`src/lib/analysis/limits.ts`](src/lib/analysis/limits.ts) and are hard caps: exceeding one degrades the scan, it never fakes data.

| Limit | Value |
|---|---|
| Recursive tree entries | 100,000 (GitHub's own cap) |
| Files whose content is fetched | 24 |
| Single fetched file | 256 KiB |
| Total fetched content | 3 MiB |
| Parallel blob requests | 6 |
| Per-request timeout | 8 s |
| Pipeline deadline | 25 s |
| Graph nodes / edges | 24 / 40 |
| Issues in report | 24 |

**What "estimated" means.** LOC is counted exactly for fetched files; for the rest it is derived from the tree's blob byte size divided by a per-language average. The UI labels it `≈ LOC` and shows how many files were counted exactly. Language shares are byte/line estimates across the eligible tree.

**Sparse graphs are allowed.** If the sampled files contain no resolvable imports, the graph has few or zero edges. That is a finding about the sample, not a failure, and the `/04` panel stays empty rather than drawing invented connections.

## Security model

- **Server-only secrets.** `GITHUB_TOKEN` is read in the route handler and never serialized. No `NEXT_PUBLIC_*` variables exist.
- **No code execution.** Only GitHub REST endpoints are called (`repo`, `git/trees`, `git/blobs`); repository code, scripts, package installs and builds are never run.
- **Bounded requests.** Hard caps on files, bytes, concurrency, timeouts and total duration; a scan cannot be used to hammer GitHub.
- **Redaction.** Credential patterns are matched in memory; only the pattern family, path and line survive. `/05` reports `value redacted`.
- **Request hardening.** 4 KiB body cap, same-origin enforcement for browser requests, `POST`-only endpoint, typed errors with no internal detail.
- **Abuse guard.** Per-client in-memory limiter (6 analyses/minute). It is per serverless instance, not global — documented under limitations.
- **Headers.** `X-Content-Type-Options`, `X-Frame-Options: DENY`, strict referrer policy, permissions policy, COOP and a `frame-ancestors` CSP are set in [`next.config.ts`](next.config.ts). `X-Powered-By` is disabled.
- **Logging.** Failures log a classification (`github RATE_LIMITED (status 403)`) — never the token, request body or raw payload.
- **No storage.** Nothing is persisted; the analysis exists only for the request.

## Current status of large-repository analysis

Validated on `vercel/next.js` (Phase 2, single controlled live scan):

| Measurement | Result |
|---|---|
| HTTP | `200` in **6.42 s** end-to-end (engine 5.58 s) |
| GitHub requests | **26** (1 repo + 1 tree + 24 blobs), all `200`, no retries |
| Tree | **34,271** blobs, **not truncated** |
| Pruned | 1,315 ignored-dir / 636 binary / 73 oversized |
| Files inspected | **24** (0.07% of eligible files) |
| Content bytes | 19.29 MB transferred (tree JSON dominates); per-file cap respected |
| Issues | 10, score 67 (fair) |
| Graph | 14 nodes, **0 edges** |

That scan exposed two defects which are now fixed: it reported itself **complete** at 0.07% coverage (now `SAMPLED COVERAGE` + partial), and it presented tree-wide file counts as "files analyzed". It also revealed that sampling was dominated by `packages/next/compiled/**` bundles, which is why vendored content is now down-ranked and workspace manifests are prioritized. The graph fix (workspace glob resolution, package-name imports, `pnpm-workspace.yaml`) is covered by regression tests; a second live scan was deliberately not run because the unauthenticated quota is shared and scarce.

## Known limitations

- **Bounded sample, not a full audit.** 24 files are read regardless of repository size. Findings describe that sample; the UI discloses it.
- **Sparse or empty graphs** are possible when sampled files do not import across modules.
- **LOC and language shares are estimates** for unfetched files.
- **Root manifests only** are parsed for dependency counts; workspace package dependencies are not aggregated.
- **Score thresholds are heuristics**, damped for small repositories. They are not comparable across ecosystems.
- **Rate limiter is per instance** — it does not coordinate across serverless instances or regions.
- **Quota is shared per IP** when no token is configured.
- **No persistence or history** — every scan starts from scratch; the ETag cache is in-memory and per instance.
- **No screenshots are committed.** Run the app locally to see the interface.

## Deployment

The app is a standard Next.js 15 App Router project with one Node-runtime route handler and no database, so **Vercel is a compatible target** (any Node host works too).

### Vercel

1. Import the repository in the Vercel dashboard (framework preset: **Next.js**; root directory: repository root). Build command `npm run build`, output handled automatically.
2. Add `GITHUB_TOKEN` under **Settings → Environment Variables** for Production and Preview. Mark it as a secret; do not use a `NEXT_PUBLIC_` name. The app still boots and serves demo mode without it.
3. Deploy. `maxDuration = 60` on the analyze route fits the Hobby limit; the pipeline's own deadline is 25 s.
4. Verify after deploy: `/` renders, demo mode completes offline, a live scan of a small public repository returns 200, and `/api/analyze` rejects a malformed URL with 400.

Or with the CLI:

```bash
npx vercel          # preview deployment (requires `vercel login`)
npx vercel --prod   # production deployment
```

Nothing is deployed by this repository's checks. No deployment URL is claimed here.

### Other Node hosts

```bash
npm ci
npm run build
GITHUB_TOKEN=… npm start
```

Set `PORT` if the platform requires it. The analyze route needs the Node.js runtime (it uses `Buffer`), not the Edge runtime.
